## M1 decisions

- Register prompt text as `system`; permissions are rule arrays and the tool set is controlled through permissions plus hooks.
- Parse model strings into `Model.Ref`; leave the model unset for inheritance. Model transforms expose metadata, but use async `ctx.model.default()` for the effective host default.
- Apply `temperature`, `topP`, and `maxTokens` through mutable context `options`; use model variants for reasoning settings. Capability metadata is best-effort and provider errors must be handled without failing setup.
- Use `edit` / `write` / `patch` as source-edit tools. Extract edit/write paths from `input.path`; inspect `patchText` for patch targets.
- Keep `execute.after` tracing and event subscription non-throwing; abort the event iterator in cleanup.
- Resolve project-relative paths from `ctx.location.directory`. Runtime data remains outside the plugin code; M0 created no product SQLite schema.

## M1 implementation and verification

- The development loader is `.opencode/plugins/delivery-team/index.ts`, which re-exports `src/index.ts`. A persistent OpenCode `2.2.0` server smoke test returned all nine team agents from `/api/agent` and `team`, `team-status`, and `team-retro` from `/api/command` after plugin activation.
- Zero-config agents have no `model` field, preserving host-default inheritance. The real smoke test confirmed the agents and commands; model override, parameter, fallback, and disabled-role behavior is covered with the fake context.
- `reasoningEffort` is mapped to a matching model variant only for explicit model routes. For inherited routes it is dropped with a warning so the agent model remains unset; this follows the V13/V14 boundary rather than sending an unverified provider option.
- Model fallback, unsupported-parameter, catalog-validation, auto-routing, and diversity diagnostics are retained in `getDeliveryTeamSnapshot(context).models.events`. They are in-memory only in M1; M2/M4 will connect them to the trace/status/report data layer.
- Config validation warnings are exposed separately in the same setup snapshot. There is no host logger on the installed Promise plugin `Context`; M1 does not write warnings to the TUI or persist events.
- `ctx.agent.reload()` and `ctx.command.reload()` replay registrations during setup. Prompt files under `<root>/prompts/<role>.md` are read synchronously inside the agent transform, so a later agent reload sees updated human-approved prompts.

## M2 implementation and verification

- **SQLite adapter.** `openDatabase(path)` selects `bun:sqlite` under Bun and `node:sqlite` otherwise, creates the parent directory, and applies `journal_mode=WAL`, `busy_timeout=5000`, and `foreign_keys=ON` before migrating. Rows returned as `null` by Bun are normalized to `undefined`. Transactions use `BEGIN IMMEDIATE` with nested savepoints.
- **Data root.** The plugin resolves the whole `.team` data root (not just the DB) against the main repository from `git rev-parse --path-format=absolute --git-common-dir`, with a fallback to `ctx.location.directory`. Worktrees therefore share one database and run directory.
- **Schema.** Migration 1 matches SPEC §10.2, including `lessons_fts` and its INSERT/UPDATE/DELETE triggers. `schema_migrations` makes fresh installs and upgrades idempotent. FTS synchronization and foreign-key enforcement are covered by tests.
- **Trace safety.** `Tracer.event` and `Tracer.toolCall` catch every database error, keep a small error ring, and call a non-throwing logger (stderr by default). A closed database is tested; tool calls do not fail because tracing failed. Tool-originated events carry `session_id`, `agent`, and `tool_call_id` inside `events.data_json`; `run_id`, `phase`, and timestamps use the dedicated columns/identity.
- **Artifact gates.** The footer parser is case-sensitive, trims values, keeps the last duplicate key, and uses the last footer block. A footer must be the final non-whitespace content. Missing artifacts, missing/not-at-end/invalid footers, non-approved specs, test failures, non-passing QA verdicts, and adversary blockers return `ok:false` with a message naming the file and expected line.
- **Spec approval.** Leaving `spec` requires both `STATUS: APPROVED` and a `decision` note matching `human_approval` (underscore, space, or hyphen). This is the documented v1 limitation: the plugin records the claim but cannot verify that a human actually approved it.
- **Tests.** Leaving `test` requires `COMMAND` and an integer `EXIT`; `RESULT: PASS` additionally requires `EXIT: 0`. `RESULT: SKIPPED` is accepted only when no component declares a test command and the run has a decision note. Per the roadmap wording, that note does not have to be recorded during the `test` phase.
- **Stack detection.** `src/stack/markers.ts` is the data table; `src/stack/detect.ts` is pure and consumes only a file listing and caller-supplied small reads. It performs no command execution, network access, or writes. Detection covers every marker row, multiple components per repository, monorepos, multi-language roots, lockfile package managers, package scripts, Makefile/just/Task targets, and CI commands. Repo-declared commands override ecosystem defaults.
- **Stack resolution.** Order is human `<root>/stack.json` → `options.stack.overrides` → the run-stored profile → detected → empty. `team_stack` persists the resolved profile to `runs.stack_json` and `<run>/stack.json`; `team_stack_update` applies a JSON merge patch, forces `source: "researcher"`, and refuses paths already owned by the human `stack.json`. When default test/docs globs apply, `team_stack` records a `gate.scope_default` event; M3's scope gate records the same event (once per run) when it actually uses the defaults.
- **CLI model resolution.** `team models` without `--run` reads the latest `models.snapshot` event written during plugin setup, because the human CLI has no access to the host model catalog. `team models --run <id>` reads the stored `run_models` snapshot. This is the M2 meaning of "live resolution"; a fresh database with no plugin setup reports that no snapshot exists.
- **CLI paths.** `--root` defaults to the main repository's `.team` directory. An explicit relative `--root` is resolved against the current working directory. `--db` optionally overrides `<root>/team.db`. Commands print JSON and use exit codes 0 (success), 1 (runtime failure), and 2 (usage).
- **Tool contract.** All team tools use plain JSON Schema with `additionalProperties: false`. Expected failures return `{ output: { ok: false, code, error }, content: [{ type: "text", text }] }`; unexpected exceptions are caught by the tool wrapper and converted to `tool_error`. Database open failure keeps the plugin loaded and makes tools return `database_unavailable`.
- **Tool output schema.** The V2 code-mode host rejects a result that contains `output` when the tool declaration has no output schema (`Tool result declared output without an output schema`). Every team tool therefore declares a permissive object schema requiring `ok: boolean` and allowing additional fields; the structured success and failure payloads remain intact.
- **Real-host smoke test.** A persistent OpenCode `2.2.0` server (`opencode serve`, authenticated via `OPENCODE_PASSWORD`) loaded the plugin, listed all nine agents and the `team`, `team-status`, and `team-retro` commands, and exposed all eight `team_*` tools in code mode. A real model session called `team_status` with an unknown run and received the expected `{ ok: false, code: "run_not_found" }` output. This smoke test caught the missing output schema above. The CLI's `team models` command also read the live `models.snapshot` written by plugin setup.
- **Run resolution.** Explicit `run` → bound calling session → parent session → the single open run (which then binds the session) → `run_ambiguous` or `run_not_found`. Parent-session resolution is tested by seeding the `sessions.parent_id` relation directly, since event-driven parent discovery is deferred to M4.
- **Loop escalation.** `team_rewind` increments the target-phase counter and refuses with `ESCALATE_TO_HUMAN` when the new count is `maxLoops + 1`; the run stays in the current phase and `loop.exceeded` is traced. `team_loop` increments the current phase and returns `ok:true` with `escalate:true` and `action:"ESCALATE_TO_HUMAN"` at the same boundary so the caller can still read the counter. Both behaviors are covered at exactly `maxLoops + 1`.
- **Terminal state.** Advancing out of `retro` moves to `done`, sets run status `closed`, and returns `terminal:true`. Further advances return `run_terminal`; status remains readable. Entering `retro` writes `<run>/report.md` with phase durations, loops, gate denials, and notes.
- **Verification.** `bun run typecheck` is clean and `bun test` covers footer/gate tables, migrations/WAL/FTS, trace failure, run repositories, every marker row, resolution order, CLI commands, run resolution, loop caps, statuses, the database-unavailable path, and a scripted run through every phase to `done`.

## M3 implementation and verification

- **Registration.** `registerGate` is called from plugin setup only when `gating.enabled` is true, and its disposer is registered with the other cleanup callbacks. A hook-registration failure is non-fatal: setup records `gate.registration: <message>` in `setupWarnings` and keeps the plugin loaded. When gating is disabled no `execute.before` hook is registered.
- **Trace contract.** Every gated tool call writes a `tool.before` event with `tool`, `message_id`, and `input_keys` before evaluation. Trace writes are fail-safe, so a closed or broken database cannot break the call. Gate decisions add `gate.denied`, `gate.unresolved`, `gate.scope_default`, or `gate.scope_skipped`; unexpected evaluation failures add `gate.error` and allow the call. Only an intentional `GateDenial` is thrown.
- **Edit phase gate.** For every tool in `gating.editTools`, all extracted targets are resolved against the project directory. Before `implement`, paths outside `<root>/` are denied with `edit_phase_blocked`; paths under `<root>/` are always allowed. A multi-file patch passes only when every Add/Update/Delete/Move destination passes. Unknown path shapes are denied conservatively with `edit_path_unknown` and an actionable extractor hint.
- **Path extractors.** Defaults are `edit` and `write` → `input.path`; `patch` → `*** Add File:`, `*** Update File:`, `*** Delete File:`, and `*** Move to:` headers in `patchText`. The optional `gating.pathKeys` map (`{ "<tool>": "<input key>" }`) overrides the path key for a tool and can also override patch parsing. This key is an M3 config addition beyond SPEC's config table; it satisfies the roadmap's configurable-extractor requirement without changing the defaults.
- **Scope gate.** Only edit tools are scoped. `tester` may edit the run root or paths matching the resolved `globs.tests`; `docs` may edit the run root or `globs.docs`; `spec` and `retro` may edit only under `<root>/`; `team-lead`, `researcher`, `developer`, `qa`, and `adversary` have no additional path scope. Paths outside both the project and `<root>/` are denied for scoped roles even when they match a glob.
- **Profile resolution.** Scope decisions use `StackService.resolveForRun(run, false)`, so the normal order (human `<root>/stack.json` → `options.stack.overrides` → stored run profile → detected → empty) is preserved. A per-handler cache keyed by run ID plus `stack_json` avoids re-resolving on every edit; it is invalidated when the stored profile changes.
- **Default globs.** When a component has no test globs, the cross-language `DEFAULT_TEST_GLOBS` apply; missing docs globs use `DEFAULT_DOC_GLOBS`. The gate records `gate.scope_default` once per run (`runs.hasEvent`) with the resolved tests, docs, and profile source. Test and docs defaults are tracked separately so a missing docs glob does not produce a misleading default event for a tester edit.
- **Missing agent.** If `execute.before` has no recognized agent, the scope gate is skipped but the edit phase gate still applies. `gate.scope_skipped` is recorded once per run. Recognized roles outside the scoped set (for example `team-lead`) do not emit this event.
- **Strict unresolved runs.** A call that cannot be tied to an open run writes `gate.unresolved`. With `gating.strict = true` the handler then throws `GateDenial` with code `unresolved_run`; with `false` the call is allowed. The message tells the agent to call `team_start` first or ask the human to disable strict mode.
- **CLI approval bypass.** The bypass check runs before run resolution, so it works even when no run is open. Shell tools (`shell` and `bash`) have whitespace normalized and are denied with `cli_approval_blocked` when the command contains `team lessons approve` or `team prompts approve`. The message asks the human to run the approval outside OpenCode.
- **Loop caps.** The gate does not increment or enforce loop counters; `team_loop` and `team_rewind` remain the only loop-cap authorities.
- **Real-host smoke test.** A persistent OpenCode `2.2.0` server was started on a temporary project with the plugin configured through `plugins[].options` and `OPENCODE_PASSWORD`, then driven with `opencode run --model opencode/deepseek-v4.1-flash-free --agent developer`. Results: a direct `write` to `src/gate-smoke.txt` was blocked during both `brainstorm` and `spec` with the documented `edit_phase_blocked` message; the file was absent; a write to `.team/gate-root.txt` was allowed during `spec`; after moving the run to `implement`, the source write succeeded; a direct `shell` call containing `team lessons approve --role developer` was blocked with `cli_approval_blocked`. The smoke also recorded a nested Code Mode `team_start` call, confirming V18. The temporary server, run, and database were removed afterward.
- **Verification.** `bun run typecheck` is clean and `bun test` passes 109 tests / 775 assertions across 14 files, including every gate branch, custom and default scopes, strict and lenient unresolved runs, path extractors, trace safety, and plugin-level hook registration/disposal.

## M4 implementation and verification

- **Always-on tool tracing.** `src/hooks/trace.ts` registers `execute.before` and `execute.after` independently of the M3 gate. The before hook records tool name, message ID, and input keys; the after hook writes `tool_calls` with session/agent/run/phase, start time, duration, output byte count, and success. Correlation uses session ID + tool call ID + tool name and a bounded LIFO stack (V18 can reuse one call ID for outer and nested calls). Calls without a matching before span still get an after row with unknown timing. Gate-denied calls skip `execute.after`; their `gate.denied` event is the record of the denial.
- **Tracing failures.** The complete before/after handler bodies are guarded. `Tracer` also catches database errors. Tests close the SQLite adapter before invoking both hooks and assert no exception escapes; a trace outage therefore cannot fail the host tool call.
- **Privacy.** `trace.captureInput` defaults to `false`; `trace.previewChars` defaults to `0`, which disables output-preview persistence. Enabling capture stores recursively redacted inputs; enabling previews stores redacted text truncated to the configured character limit. Trace event data, inputs, and previews are sanitized at persistence and `team trace` applies redaction again on export. Secret-looking keys and common bearer, API-key, GitHub, AWS, Slack, JWT, and private-key patterns are redacted. Byte counts and timings remain available without persisting tool contents.
- **Event ingestion.** Setup starts `ctx.event.subscribe({ signal, types })` as a background task and never waits for the first event. Cleanup aborts the iterator with a bounded wait. Events use the V2 envelope `{ type, created, data, location? }`; project filtering uses `location.directory`. `session.created.data.parentID` builds parent links, `session.model.selected.data.model` records the selected model, and `session.step.ended.data` supplies `assistantMessageID`, `tokens.input`, `tokens.output`, and authoritative per-message `cost`. Cumulative usage updates are not summed. Child sessions inherit the parent's run, and messages seen before a run binding are backfilled when the session is bound.
- **Event fallback and limitation.** `getDeliveryTeamSnapshot(context).events` exposes `subscribed`, `unavailable`, or `closed`, including asynchronous stream failures; failures are also added to `setupWarnings` and traced when the DB is usable. The tool executor context still creates/binds sessions if the event API is absent. Late run binding propagates to already-recorded descendant sessions/messages. Message/token/cost totals and event-derived child-session details are unavailable when ingestion is down. The host event stream is live, not a replay: a `session.created` or model-selection event emitted before plugin setup may be missed, so a context-created lead session can have no recorded start event and a message's model can be null.
- **Status and report.** `team_status` now includes exact tool/failure, gate denial/unresolved, loop, message, token, and cost counters; the ten recent events and tool calls are included. Entering `retro` writes a full `<run>/report.md` with phase durations (using `closed_at` for completed runs), tool totals grouped by tool and agent, failures, messages grouped by agent/model with token/cost totals, sessions, loops, gate denials, and notes.
- **CLI.** `team runs [--open]` returns JSON run summaries with age; `team report <run>` renders Markdown; `team trace <run>` emits structured JSON and `--jsonl` emits chronologically sorted line-delimited event/tool-call records. Trace exports redact secret fields and common secret strings by default. Existing `--root` and `--db` selection remains available.
- **Real-host smoke.** OpenCode `2.2.0` loaded the local plugin in a temporary project and a model session called `team_start`, `shell`, and `read`. SQLite showed the outer `execute` and nested `team_start` as distinct calls despite their shared V18 call ID, plus successful shell/read rows with durations and byte counts. `session.step.ended` ingestion populated four messages and token totals; the executor context bound the lead session to the run. `team_status` returned tool/message counters and recent events. `team runs`, `team report`, and `team trace --jsonl` all succeeded; JSONL parsed as 15 event/tool-call records. A later persistent-server invocation after the provider's free-model quota was exhausted returned the expected provider error before tool execution; the earlier real-host smoke had already exercised the plugin and CLI successfully. The temporary smoke projects and server data were removed.
- **Verification.** `bun run typecheck` is clean. `bun test` passes 130 tests / 898 assertions across 17 files, including privacy defaults/redaction, nested-call correlation, DB failure safety, event filtering/inheritance/degraded mode/cleanup/late binding, report rendering, CLI exports, and status counters.

## M5.1 implementation and verification

- **Lesson proposals.** `team_lesson_propose` requires a role (one of the nine or `*`), a 20-300 character single-line imperative sentence, optional evidence, and an optional normalized stack tag (default `*`). Rows are inserted as `proposed`; no tool can approve, reject, or retire a lesson. The retro prompt asks for lesson proposals and complete prompt-proposal files, and the retro role lists the tool in `toolNeeds`.
- **Duplicates and cap.** Duplicate detection queries `lessons_fts` for same-role candidates and rejects token-Jaccard similarity at or above 0.8 with `duplicate_lesson` plus `existing_id` and `existing_status`; rejected lessons are ignored. Each source run may create at most 10 proposals (`proposal_cap_reached`).
- **Schema.** Migration 2 adds indexes for lesson status/role/stack, lesson source run, and prompt-version role/status. Fresh installs apply `[1, 2]`; version-1 databases upgrade with `[2]`.
- **Verification.** `bun run typecheck` is clean. `bun test` passes 142 tests / 941 assertions across 18 files, including validation boundaries, stack normalization, FTS duplicate detection, rejected-lesson exclusion, per-run caps, migration 1 to 2, tool registration, and the no-approval invariant.

## M5.2 implementation and verification

- **Ranking.** `LessonsRepository.rankApproved` filters `status='approved'`, role `IN (role, '*')` (or `role='*'` when the role is unknown), and `stack_tag='*' OR stack_tag IN (<stored run languages>)`. It runs an FTS5 `MATCH` over the tokenized run title plus up to 4,000 characters of `spec.md` with the footer block removed, orders matches by `bm25(lessons_fts), id`, then fills any remaining `topN` slots from `hit_count DESC, created_at DESC, id`. Seen IDs are deduplicated and the result is capped at `topN`.
- **Injection.** A single context hook always registers during setup when registration succeeds. It applies model request options first (existing behavior), then calls `createLessonInjectionHandler`; a registration failure records `context.registration` and remains non-fatal. The handler resolves the run through the session or parent chain, parses languages from the stored `runs.stack_json`, and performs no stack detection, filesystem scanning outside the run's `spec.md`, or network I/O. A missing role injects `role='*'` only; an unresolved session/run skips injection. Unexpected failures are traced as `lessons.injection_error` and never escape.
- **System shapes.** `appendSystemSection` appends to string systems, mutates arrays of text parts in place, converts a single text part into an array, and creates an array for a missing or null `system`. An identical existing section is not appended twice. Unknown shapes are refused safely and traced as `lessons.injection_skipped`.
- **Budget and hits.** `selectLessonSection` adds lessons in ranked order and stops before the first lesson whose text would exceed `lessons.budgetChars`; the header and role labels are excluded from the count and lesson text is never truncated. `hit_count` increments only after the section is appended. The `lessons.injected` event records lesson IDs, count, characters, role, languages, `top_n`, `budget_chars`, and whether the spec summary was used.
- **Verification.** `bun run typecheck` is clean. `bun test` passes 154 tests / 1006 assertions across 19 files, including end-to-end hook injection, approved-vs-proposed filtering, role and stored-stack filtering, unknown-role fallback, `topN`/budget boundaries, hit counts, trace payloads, system-shape compatibility, and never-throw behavior.

## M5.3 implementation and verification

- **Lesson CLI.** `team lessons [--status <status>]` lists rows as JSON and validates the filter against `proposed`, `approved`, `retired`, and `rejected`; `list` is also accepted as an explicit subcommand. The decision subcommands change the status and only update `decided_at` when the status actually changes, so repeated decisions are idempotent (`changed: false`). Approval and rejection can move a lesson from any prior status; retirement is limited to approved lessons, and retiring a proposed lesson returns `invalid_transition`. Missing IDs return `lesson_not_found`.
- **Export.** `team lessons export` writes only approved lessons to `<root>/lessons-export/`. Wildcard lessons go to `all.md` and every other role to `<role>.md`, with non-`*` stack tags shown as a Markdown label. Lessons are sorted by ID for stable output. Each run rewrites the current role files and removes obsolete known role files (for example after retirement or rejection) so the directory always reflects the approved set; unrelated files are left alone. The JSON result reports the directory, role list, files, counts, and removed files.
- **Stale report.** `team lessons stale` is report-only. It flags approved lessons with `hit_count >= 5` whose evidence is missing or blank, sorted by hit count then ID, and includes `reason: "high_hits_without_evidence"` and `age_days`. It never changes status; humans retire lessons explicitly.
- **Safety.** The CLI remains human-only and is not exposed as a tool; the existing shell gate continues to block the approval command. The CLI prints structured JSON like the other `team` commands and uses exit code 2 for usage errors and 1 for command failures.
- **Verification.** `bun run typecheck` is clean. `bun test` passes 158 tests / 1,073 assertions across 20 files, including listing and status filters, help and unknown-subcommand handling, idempotent decisions, invalid transitions and missing IDs, export contents and pruning, stale criteria, and report-only behavior.

## M5.4 implementation and verification

- **Proposal discovery.** The retro prompt asks for a complete prompt in `<root>/proposals/<role>.<timestamp>.md` and a filename-safe UTC timestamp. When `team_advance` leaves `retro`, the plugin scans the proposal directory, accepts only regular files with a known role and safe timestamp, hashes their contents with SHA-256, and records new `prompt_versions` rows as `proposed` with the source run. A scan error is traced and does not prevent the run from advancing. `team prompts list` also scans proposals so files are discoverable if a run exited before registration.
- **Prompt CLI.** `team prompts list` lists all recorded versions; `approve`, `reject`, and `diff` accept `<role>.<timestamp>` or the `.md` filename, optionally prefixed by `proposals/`. The stable `file`/`path` identify the proposal source; `current_path` identifies the active override for an approved row. `diff` compares a proposal with the currently approved override, or with the built-in prompt when no override exists. Rejection records `decided_at` and keeps the proposal file for reference. Repeated rejection/approval is idempotent; invalid status transitions return `invalid_transition`.
- **Approval.** Approval moves the proposal to `<root>/prompts/<role>.md`, stores its current SHA and decision time, and transactionally marks any previous approved version for that role `superseded`. The CLI uses a rollback file move if the database update fails. Its result includes the approved path and `restart_required: true`.
- **Reload and safety.** The CLI runs outside the plugin host, so approval requires restarting OpenCode; setup rereads approved override files and reloads the agent transform. Prompt resolution requires the file's SHA to match an `approved` `prompt_versions` row, so unregistered edits under `prompts/` and pending files under `proposals/` are never active. Existing manual overrides must be proposed and approved to satisfy this check. Prompt management remains CLI-only; no agent tool can approve, and the shell gate continues to block agent attempts to run human approval commands.
- **Verification.** `bun run typecheck` is clean. `bun test` passes 162 tests / 1,112 assertions across 21 files. Coverage includes retro-exit proposal registration and source-run attribution, list/diff/reject/approve behavior, SHA and superseding statuses, file movement, empty-proposal rejection, rejection of unregistered prompt edits, pending-prompt isolation, and loading the approved prompt after a fresh plugin setup (the documented restart path).

## M6.1 worktrees and concurrency

- **Feature gate and creation.** `team_worktree` is registered only when `worktrees.enabled` is true (default false). Names match `^[a-z0-9-]{1,40}$`; relative `worktrees.baseDir` is resolved from the main repository root, and the resulting worktree must be outside that root. Creation uses Git argument arrays to add `<baseDir>/<run>-<name>` on `team/<run>/<name>`. Existing paths/branches are rejected rather than forced or reused. A non-Git project returns `not_git_repository` with the sequential-development fallback, and the plugin never deletes worktrees.
- **Agent workflow.** The lead only parallelizes independent developer tasks when the tool is available. Each developer creates a uniquely named worktree and uses absolute paths for file tools and `cd <returned-path>` for commands. Developers commit their completed branch; the read-only lead coordinates integration through a developer assigned to the main checkout, reviews the result, and records a decision note. Worktree cleanup stays manual.
- **Visibility and shared state.** `team runs` parses `git worktree list --porcelain` and reports delivery-team branches with path, branch, run/name, and current run phase/status. It tolerates non-Git directories and does not mutate worktrees. Worktree plugin contexts resolve `.team/` against the main repository, so all workers share its SQLite database and run artifacts.
- **WAL startup under concurrency.** `openDatabase` configures `busy_timeout` before WAL setup, skips resetting WAL when the database is already in WAL mode, and retries transient `SQLITE_BUSY`/`SQLITE_LOCKED` errors while enabling WAL. This avoids recovery-time lock failures when separate worktree processes open the shared database together.
- **Verification.** `bun run typecheck` is clean. `bun test` passes 167 tests / 1,180 assertions across 23 files. Coverage includes feature-gated registration, safe names, Git and non-Git behavior, two worktrees for one run, manual-retention/listing behavior, and two child plugin processes calling `team_advance` on distinct runs while writing trace rows through the same WAL database without lost events or `SQLITE_BUSY` failures. No dependencies were added.

## M6.2 evaluation harness

- **Tasks and presets.** `evals/tasks/<name>/` provides task text, a fixture, and versioned criteria. Shipped fixtures cover TypeScript, Go, and Python. Criteria reference `file_exists`, `regex`, or a `stack_command` key; command criteria resolve from that fixture's Stack Profile rather than hardcoding toolchains. User-authored model presets live in `evals/models/<name>.json`; `host-default` inherits the OpenCode default without embedding a model ID.
- **Runner.** `team eval run [task...] [--models <preset>]` copies each fixture into an isolated temporary project, copies only currently approved prompt overrides into a temporary data root with their approved SHA rows, writes local plugin options, and invokes the pluggable headless runner. The default adapter uses `opencode --standalone run --print-logs --auto`; tests inject a fake runner and make no provider calls. Criteria run after the task, inside the copied fixture, using bounded argv commands derived from the Stack Profile. Symlinks and escaping paths are rejected.
- **Snapshots and results.** `prompt_set_sha` hashes the effective built-in/approved prompts; `model_set_sha` hashes the preset plus the resolved model snapshot. One `eval_runs` row is stored in the caller's main database per task. `score` is a weighted percentage (0–100); `details_json` retains per-criterion outcomes, status, run id, loops, cost, tokens, and runner result without storing full command output.
- **Reports.** `team eval report [--by both|prompt_set_sha|model_set_sha]` groups results by prompt/model snapshots and reports count, mean score, loops, cost, and per-task statuses. Evaluations remain CLI-only; they are not registered as an agent tool.
- **Verification.** `bun run typecheck` is clean. `bun test` passes 172 tests / 1,205 assertions across 24 files. The end-to-end eval pipeline test uses the `ts-slug` fixture with an injected runner, executes its Stack Profile test command, and verifies persisted SHA snapshots, score, loops, cost, and report grouping. No provider call is made by automated tests; live headless runs require a configured model/provider.
